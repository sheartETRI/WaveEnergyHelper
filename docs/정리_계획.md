## 2. 정리 전 구조와 판단 기준

운영 진입점은 `main.py`, `scripts/push_alarms.py`, `scripts/alarm_cli.py`입니다. `scripts/sweep_scan_report.py`는 별도 수동 보고서 경로입니다.

정리 전 세 운영 진입점에서 Python AST의 import 문을 재귀 추적한 결과, 조사한 모듈 집합 중 73개가 정적으로 도달 가능했습니다. 그중 `analysis` 40개, `display` 13개, `validation` 1개이며 `narration`은 없었습니다. 이는 함수 내부 import를 포함하는 보수적 결과로 실제 매 실행 호출 목록은 아닙니다. 문자열 기반 동적 import, 파일 경로, 테스트·수동 실행 경로는 별도 확인해야 합니다. 이 숫자를 삭제 판정에 사용하지 않습니다.

정리 전 주요 경계 문제는 다음과 같았습니다. 운영에서 검증 스크립트를 가져오던 경로와 notify의 UI 의존은 공용 `tracking`으로 전환했습니다.

```text
main.py → display.ma60_turn_tracker → validation.wave_ma60_turn_probe
        → display.divergence_flag   → validation.wave_ma60_turn_probe

notify.events / notify.ledger → display의 추적·구조·다이버전스 계산

display.lw_gate_context → analysis의 상위 시간봉 게이트·구조 기준선
                       → 추가 분석·연구 모듈
```

`validation`에는 실행 코드와 결과물이 섞여 있고, `display`에는 화면 렌더링 외에 알림이 재사용하는 계산도 있습니다. 화면에 연결되지 않은 기능과 실행에 필요 없는 파일은 별개입니다.

**근거:** `charts/lw_builder.py`는 약 930행으로 데이터 변환·HTML·JavaScript를 포함하고, `scripts/push_alarms.py`는 약 740행으로 CLI·데이터 준비·순회·요약을 함께 담당합니다. 행 수만으로 문제를 판단하지 않고 변경 빈도와 책임 경계를 기준으로 나눕니다.

- [x] LW의 데이터 직렬화와 화면 템플릿·상호작용 코드를 분리한다.
- [x] 폴러의 CLI, 마감 봉 준비, 순회 실행, 일일 요약을 기존 notify 구조와 맞춰 분리한다.
- [x] 외부 차트 라이브러리 원본·라이선스·해시 검사를 유지한다.

**완료 기준:** 기존 진입 명령과 함수 계약이 유지되고, 차트 상호작용·알람 표시·일일 요약·중복 방지가 같은 결과를 낸다.

### C11. 운영 설정과 실행 안내

**근거:** 앱 설정은 `config/settings.py`, 실제 푸시 대상은 `scripts/push_alarms.py`의 `PUSH_TARGETS`, 발송 제외 종류는 `notify/plan.py`에 있습니다. systemd 예시에는 환경별 사용자·경로 치환이 필요합니다.

- [x] 설정별 실제 소비자와 변경 효과를 정리한다. 역할이 다른 설정을 이름만 보고 합치지 않는다.
- [x] 실행·중지·재시작·로그 확인·API 수신 실패·발송 실패 대응 절차를 문서화한다.
- [x] dry-run도 데이터 수신은 할 수 있다는 점과, 테스트 전송은 실제 외부 발송이라는 점을 명시한다.
- [x] 토큰·이력·ledger·저장소 경로와 백업·복원 방법을 운영 안내에 정리한다.

**완료 기준:** 새 환경에서 같은 감시 대상과 발송 정책을 구성할 수 있고, 설정 위치·상태 파일·로그를 찾을 수 있다.

### C12. 진입점과 구형 알림의 추가 분리
